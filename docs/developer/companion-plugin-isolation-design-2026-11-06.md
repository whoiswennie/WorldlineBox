# 伙伴原生插件环境与按需进程设计

日期：2026-11-06。状态：本轮实现记录与后续隔离设计。已实现自动私有环境绑定、租用与原生空闲探测、保活、能力目录查询和带回滚的环境升级；任意插件的强隔离与同进程能力组合仍有下述边界。目标是在尽量保留 DSH 原生插件生态的同时，让伙伴独立配置插件，并避免用户手工维护大量实例和大量常驻进程。

## 推荐结论

保留一个共享的不可变 DSH 程序版本；普通伙伴继续使用共享原生环境。有独立插件配置、外部平台账号或常驻服务的伙伴，由宿主自动建立持久的私有原生环境。环境目录长期保存，Host 按实际需求启动并在真正空闲后退出。用户配置的是“这个伙伴的插件”，不是创建和维护 DSH 实例。

同进程的 Agent preset 能隔离明确支持作用域的能力，但不能承诺任意社区插件都能在一个进程内独立运行。QQ 等外部连接插件应先按独立环境接入；只有原生能力、配置、状态和卸载测试都证明可共享时，才合并到能力组。是否共享账号也是显式配置，不能仅因插件列表相同而合并。

“不常驻 N 个进程”可以通过惰性启动、并发上限和空闲回收实现；若 N 个插件各自需要持续监听消息且不能在一个 Host 内安全隔离，同时在线就确实需要对应的活动运行资源。产品应显示真实的连接模式，而不是把正在监听的进程误判为空闲关闭。

## DSH 的同进程能力与边界

研究用的本地 DSH 源码在相邻 `deepseek-harness` 目录；其根 `package.json` 标为 `0.2.1-rc.3`，不能仅凭该源码声称已在 `0.2.2-rc.1` 上验收。最终集成需对实际安装版本分别记录原生测试证据。

原生代码证据：

- `packages/preset/agent-preset-registry/src/index.ts` 的 `register()` 接受独立 `{ id, plugins }` 定义，并建立 scope；`mount()`、`select()` 将 Agent 绑定到对应 composition。`Generation` 记录使用者，退休且引用归零后才 dispose，已有 Agent 可保留旧 revision。
- 同目录 `mount.ts` 中 `mountPreset()` 审核插件加载失败和服务泄漏，拒绝发布到根 realm 的服务，要求相应 isolate realm。共享同一 preset revision 的 Agent 共享其 composition；需要不同配置时必须是不同配置 revision，而不是只换显示名称。
- `packages/core/tools/src/index.ts` 的 `restrict()` 仅接受 scoped context，工具限制沿 scope 链取交集；自身注册的工具不受该 mask 影响。`guard()` 是执行阶段的单调拒绝检查，不能被普通 `tools/pre-execute` 监听器的 allow 绕过。
- `packages/subagent/subagent/src/child-agent.ts` 将父级 composition 的 tool filter 应用于子代理。WorldlineBox bridge 的 `recordFor()` 还把后代工具调用映射回原任务进行检查和记账。

由此可以原生支持：同 Host 不同 Agent preset、工具/技能选择、提示词和 scoped 服务配置。不能由此推出：任意插件的模块单例、`process.env`、监听端口、全局定时器、外部账号、硬编码磁盘目录也自动隔离。原生 isolate realm 是服务解析范围，不是 OS 或 JavaScript 模块沙箱。

bridge 通过 `worldlinebox-companion-v2` 使用原生 preset；伙伴的任意原生插件配置隔离依靠私有 Host 环境，而不是为每个伙伴随意修改共享 preset。`/plugins` 调的是 Host 级 `pluginManager`，不是某个任务的临时插件集合。因此不能通过临时停用默认实例插件来实现伙伴选择，那会直接改变普通 Web 与其他伙伴的可用能力。

## 分层管理，保留原生生态

| 层 | 负责什么 | 稳定身份与变更规则 |
| --- | --- | --- |
| 程序版本 | DSH、Node 和不可变资源 | 共享 runtime；升级不覆盖旧程序，旧版本保留到没有回退引用。 |
| 原生环境 | 原生配置、插件包清单、插件配置、登录态、原生 Session 与插件持久状态 | 独立稳定环境 ID；与伙伴及程序版本分离。升级仅更换其 runtime 引用。 |
| 能力配置 revision | scoped preset、已安装插件来源、工具/技能选择、配置摘要 | 不就地修改正在执行的任务；新任务引用新 revision，旧任务保留原绑定。 |
| 任务 | 本任务业务上下文、附件绝对路径、能力选择、权限、结果与重试去重 | 接收时持久绑定环境、revision 和原生 Session；后续恢复沿用，不跟随 UI 当前默认实例跳转。 |
| Host 租用 | 谁正在使用进程、是否允许空闲退出 | 由宿主计算，不交给模型自行增减；进程退出不删除原生环境。 |

默认不定制的伙伴不额外创建环境。首次配置私有插件时自动创建，安装仍交给原生 manager；UI 使用原生插件配置页面或官方配置协议，不自行复制一套插件 schema。程序包可共享缓存，但实例的账号、配置和可写状态不共用。不要手工复制 pnpm 的链接目录；继续使用原生依赖恢复流程。

共享能力组是可选优化：组合键至少包含程序/插件版本、规范化配置摘要、凭据作用域、插件状态作用域和 keepalive 策略。只有使用者明确允许共享账号及状态，且插件隔离验收通过，才允许共用一组。凭据值不进入摘要、提示词和导出的诊断。

## 最小的任务能力策略

普通业务任务默认使用标准环境和标准 preset；指定的 QQ/外部平台任务才附加相应能力。私有环境里带有全局监听或 middleware 的插件时，普通任务仍派到标准环境，避免仅隐藏工具名却继续受到该 middleware 的影响。任务对资料的访问通过宿主核验后的绝对路径提供，不把环境管理记录写进业务提示词。

接收任务时固化以下事实，均由 Router 的宿主接口管理：所选环境和能力 revision、准许的原生工具/技能、外部账号/目标范围、本任务子代理继承规则、原生会话绑定。Worker 的完整业务说明只含用户要求、相关上下文、附件路径、目标与验收依据。插件安装、环境锁、进程租用和重试参数保存在宿主记录。

实现时应把“OS/文件权限范围”和“原生能力选择”分开：允许完整文件访问不等于自动给出所有外部平台发送工具。普通任务保持原生基础工具；本任务显式选择的插件工具/技能作为附加能力。能力发现必须读取目标环境的实际 registry，记录摘要，发现缺失、重名或版本变化时给出具体诊断，不静默替换为别的插件。

工具声明与真正执行必须使用同一 policy：模型看不到的能力也不可经 PTC、子代理、原生工具名直接调用绕过。继续使用原生 `restrict()` 加执行阶段 `guard()`；回调工具也逐项校验。任务取消、移除或暂停后的新工具调用应被拒绝，旧任务的迟到回调不能授权新任务。插件提供独立启动监听服务时，监听属于环境租用，不由工具声明是否可见决定。

这是产品隔离与路由策略，不是运行任意恶意 Node 插件的安全沙箱。插件仍可能以当前 OS 用户访问硬编码全局路径；遇到这种行为需标记为无法保证环境隔离，不应通过 UI 承诺每伙伴完全隔离。

## 按需 Host 生命周期

在现有 `ensureHost()` 启动合并基础上加入宿主持久绑定与活动租用。建议惰性启动是默认，空闲延迟可设为 2 分钟，活动 Host 并发上限作为资源策略配置；这些是建议默认值，需要实际启动成本和内存测量后确定。打开设置不应无意唤醒所有伙伴环境，目录浏览可先读已保存元数据，进入需要原生配置的单个环境才启动它。

以下任一条件存在时均不算空闲：

- 接收、排队或运行中的原生工作，正在投递或恢复的输入；
- 未回答的有效原生问题、未结束的工具调用或子代理；
- 需要保持运行的后台 job、终端命令或原生插件活动；
- 已打开的工作台、CLI 终端或需要保活的外部连接插件；
- 原生状态尚未 flush 的临界区、正在变更配置或升级环境。

排队任务可按调度决定尚未启动 Host，但不能被空闲回收器误作完成或丢弃。暂停任务仅在原生工作已停且持久状态已 flush 后释放运行租用，恢复时仍使用同一环境、任务、Session。有效问题如果不能在 Host 退出后无损恢复，应保留租用，不以“没有模型请求”判断空闲。

真正空闲时先锁住新准入、再次确认本代租用为空，原生 flush 后停止 Host。若这期间新请求到达，取消退出或在退出完成后重新启动，避免一方用旧 client、一方关闭进程。不同任务的租用独立释放；停止一个任务不能停止其他任务或 QQ 监听。超时或原生状态不明时保留环境绑定并显示原因，不能另起一个环境重放已有副作用。

QQ 常在线与“用时连接”应分别呈现。用时连接可节省资源，但离线期间能否收到消息取决于平台及插件本身；不可承诺离线实时收件。服务插件只有在提供可靠的活动/保活信息后才允许自动回收；未知能力先保留进程并提供明确停止入口。

## 安全迁移与升级顺序

1. 先加入环境记录和伙伴绑定的持久化，不改变已有默认实例、旧 lane 或任务。旧任务从已有原生绑定认领，不能按伙伴新配置静默迁走。
2. 新定制环境以事务记录“准备中”，创建稳定目录，复制经过选择的配置模板，通过原生 manager 安装插件；验证原生能力、账号范围和配置隔离后提交为可用。失败保留可读诊断并回收未提交的环境，不碰默认实例。
3. 先对新任务启用目标环境选择及能力 policy；恢复任务继续使用原绑定。只有用户明确恢复或重新安排任务时才新建执行，不能把迁移当重试。
4. 增加生命周期租用与活动探测后，再开启自动空闲退出。没有足够原生活动证据的插件不启用回收，直到其契约或测试补齐。
5. 升级前阻止新准入并等待/暂停现有活动，关闭工作台写入，保存完整一致快照和旧 runtime 引用；保留 Session、附件、storages、插件配置及登录态。现有模板 clone 排除这些目录，不能用于此步骤。
6. 保持环境 ID/路径不变，将 runtime 引用切到新不可变版本；运行新版本的原生依赖恢复和必要迁移。不得用默认配置覆盖已有 profile，插件版本变化需显式策略。
7. 用原生健康检查、插件加载、实际能力发现及持久会话恢复验收后，提交升级完成。失败时停止新 Host，恢复旧 runtime 和快照再启动旧环境；数据曾发生向前迁移时，仅改回版本号不足以回滚。
8. 保存升级/回滚记录与原生诊断，保留旧版本直到没有任务、环境或快照引用。任何阶段都不自动重放聊天消息或外部发送。

同一配置 revision 的原生 preset 已有引用退休机制可以复用；但其内存 generation 不替代环境配置、绑定和迁移日志的磁盘持久化。已开始 Session 的 preset 切换受原生锁定限制，应沿用旧 revision 或在明确新 Session 中应用新配置。

## 建议的伙伴设置体验

在“编辑伙伴”中提供“执行器与插件”：默认显示“使用共享环境”；选择“为此伙伴配置插件”后自动准备独立环境并显示其状态。插件安装、原生设置、登录、能力概览与失败重试都在这个伙伴下完成，带出目标伙伴身份。高级用户可从链接打开对应原生工作台。

进程策略以“用时启动，空闲退出”和“保持连接”呈现。需要在线消息的插件在卡片上说明当前连接模式与保活原因。启动、休眠、升级状态不占据聊天大横条；活动环境和资源占用在详情中查看。

启动器可将自动管理的环境折叠在“伙伴环境”区域，不把它们混入用户手工实例列表。伙伴切换程序版本时显示“升级此伙伴环境”，保留插件和账号；共享环境的全局插件变更明确显示影响范围。不要提供一个看起来只影响当前伙伴、实际却停用共享实例插件的开关。

## 必须新增的原生验收

| 场景 | 必须核验的原生事实 |
| --- | --- |
| 同程序、不同私有环境 | 相同 `runtimeId`，不同 Home/agents/partition；A 装插件、改配置、登录与写状态不改变 B 的清单、配置和原生能力。 |
| 同 Host scoped preset | 两个真实 preset 使用不同配置，服务和工具结果各自匹配；A 的副作用不进入 B，dispose A 不破坏 B。加载泄漏根服务的 fixture 应被原生拒绝。 |
| 普通任务与 QQ 任务 | 普通任务能力及工具结果不含 QQ 插件内容；QQ 任务只使用对应账号/目标；两者并发时插件 middleware 和系统提示词不串环境。 |
| 绕过与后代 | 子代理、PTC、手工构造工具调用都不能执行本任务未选择的能力；本地回调工具与继承工具分别覆盖，取消后拒绝新调用。 |
| 惰性启动与并发 | 1000 个未使用的伙伴不启动 1000 个 Host；同环境并发首次请求只启动一次；并发上限排队不丢任务。 |
| 租用退出竞争 | 停止 A 任务不影响 B 或保活插件；未回答问题、后台 job、子代理、工作台阻止回收；最后租用释放并 flush 后才退出。新准入与退出竞争不返回失效 client。 |
| 重启与恢复 | 空闲退出后重新启动能够恢复原生 Session、问题和任务绑定；不会重新发送旧平台消息或重跑已发生的工具副作用。 |
| 原生升级 | 相同环境 ID/路径升级，插件配置、凭据、历史、附件和 storages 保留；实际加载及会话恢复成功。原生迁移失败后恢复旧版本及快照，数据一致。 |
| 故障注入 | 安装失败、插件加载失败、进程异常退出、flush/停止超时、磁盘写失败保持清晰状态，不偷偷切换环境或重放业务。 |
| 资源与退出 | 记录每个实际版本的冷启动、热启动、空闲内存与退出后残留进程；关闭软件无未认领 Host，退出日志可追踪。 |

优先扩展现有 `tests/helpers/companion-dsh-native-broker.ts` 与 `tests/worker/dsh-native-web-ecosystem.test.ts`，使用临时独立 Home 和真实安装版本；fixture 插件应有不同配置的工具、scoped 服务、一次性副作用计数和可观测 keepalive。先运行无需模型的原生注册/隔离/生命周期测试，再以少量真实模型调用验证选择、子代理继承、恢复。不要用模拟 registry 或仅匹配提示词代替这些边界的验收。

本轮能力入口位于伙伴聊天顶部与启动器“伙伴能力”页，复用原生插件/技能管理和市场；原生插件包与实际可调用工具/技能分开展示，目录使用真实原生注册结果，不按插件名称猜测。伙伴总开关使用统一 `companion.runtime` 命令；关闭后 UI 不再自动查询会唤醒 Host 的原生目录。

界面和文档不能把所有任意插件都描述为无影响热替换。原生全局注册的新工具可在后续步骤使用；预设内部能力变更对新任务立即生效，已有会话保留原来的能力范围，因为原生 SDK 没有关闭入站并原子重绑历史 Agent 的协议。目录显示 `scope.pending` 时，用户可选择“应用待更新能力”，由宿主在没有活动任务和租用后重连原生环境，保留任务记录，不自动重放已有任务。停用或替换后，尚未派发的旧工具可能失效，正在执行的插件体是否继续取决于插件自身的 dispose 行为；需要重启的变更等待空闲。外部平台持续监听是否被 idle 证明识别取决于原生插件，应使用“保持连接”表达明确的在线需求。

对用户宣称支持的范围必须以实际执行版本和验收结果为准。上面的能力组共享、任意插件的细粒度任务选择和通用插件安全隔离是进一步设计，不因已有私有目录和按需进程就视为全部实现。

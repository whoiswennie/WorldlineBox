# 伙伴私聊受众与任务回执隔离

## 问题与边界

伙伴私聊只有两位伙伴参加，用户旁观。正文应直接回应另一位伙伴；向用户转达使用独立的发送或正式委派交付通道。

旧实现虽然将任务通知的 `recipientIds` 限定为任务所有者，但通知正文仍作为房间消息进入历史投影。另一位伙伴随后构建 Router 上下文、准备记忆或投影 VCP 历史时，可能读到对方尚未公开的 Worker 回执。共享 DSH 账号、插件和进程不应扩大这些数据的可见范围。

## 修复

- `room.replyAudience` 和本轮受众提示明确当前对话对象，包括以任务服务为触发者的回复。跨聊天工具的发送结果不能被当成本房间已经公开的数据。
- Main 使用统一的消息可见性规则检查房间成员、任务通知收件人与真实任务所有者；普通伙伴已发布的消息和文件仍属于房间共享内容。
- Router 历史查询在 SQL `LIMIT` 之前按身份过滤；群聊参与判断只接收公开消息。记忆准备和 VCP 原文投影采用相同规则，投影游标仍跨过被跳过的内部通知。
- `chat_read_message`、附件目录、任务状态和完整回执读取维持同一边界。猜测另一位伙伴的任务或消息 ID 不提供原始回执读取权限。
- 正式委派不受影响：接收方调用 `companion_delegation.result` 显式交回后，请求方读取自己代理任务中的交付内容；这不开放对方其他任务或 Worker 内部轨迹。
- 旧群聊和伙伴私聊在安全边界上进行一次定向迁移：撤回错误投影的私有通知来源，隔离旧 Router 上下文和压缩摘要，从合法已发布聊天重建。聊天记录、用户可见任务卡、Worker 会话及原始工具回执继续保留。未结清的原生投递不迁移或重放。
- VCP 定向修复仅删除受私有回执污染的笔记及其派生笔记，不沿混合笔记扩大到其他公开原始来源。模式随撤回记录持久保存，崩溃恢复仍使用相同范围；正常用户忘记操作继续使用完整来源撤回规则。混合撤回队列按模式分别投递，整页完成才推进游标。
- VCP 使用定向通知撤回模式：删除受污染记忆及其派生笔记，保留同一笔记引用的独立公开原文；普通用户“忘记”仍保留完整来源递归撤回语义。定向模式按笔记耐久记录，崩溃修复不会将它误当作普通忘记扩散；宿主按来源类型拆分撤回批次，全部确认后才推进游标。

## 验证

`bot-context`、`bot-peer-contact`、`bot-task-private-receipts` 和 `bot-task-notice-audience-migration` 覆盖当前上下文、真实 BotService 调度、SQL 工具访问、记忆投影、旧上下文隔离，以及显式分享后的正常协作。

`bot-task-notice-memory-withdrawal` 验证协议参数、混合撤回批次和回执丢失重试；`bot-task-notice-memory-native` 使用实际 VCP 及 Rust 索引、局部嵌入协议夹具，在定向撤回落盘后让子进程真实退出，再冷启动修复，核验污染笔记及派生索引已删除、公开原文和独立笔记仍可读。该测试不评价嵌入模型推理或语义相关度。

可重复的真实模型验收：

```powershell
node scripts/verify-bot-peer-audience.mjs --real
node scripts/verify-bot-peer-audience-migration.mjs --real --max-posts=6
```

验收使用隔离档案和当前已配置的官方 DeepSeek OpenAI 兼容接口，检查私有标记不进入请求，公开信息可正常回应，任务完成回复仍面向聊天伙伴。迁移验收另覆盖旧 AppBrain 历史和摘要、环境暂停及群聊。测试中的 Worker 回执为合成证据，不声称评估真实 DSH 执行或 VCP 语义召回质量；生产账号配置和聊天数据库不被修改。

本次两套真实模型验收的有效运行各 3 次请求、各 3 个场景通过。另以真实 VCP 进程和 Rust 索引验证定向撤回中断后恢复：污染和派生笔记删除，公开历史及独立笔记的向量保留，重复修复不扩大范围，普通忘记仍递归生效。对应回归为 `bot-task-notice-memory-native.test.ts`。

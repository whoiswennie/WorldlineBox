# 便携工具的仓库管理与旧目录修复

拉取 `f136efd` 后，仓库使用公开发行包配方的清单锁 `9ec34c8e4da00ddfd383fcb54cdc07f20d9c6b79dd8f67fbb3dfba7e04e7996f`，本机被 Git 忽略的目录仍是旧清单 `3476588e5cb935f3a72a778c08d163c6b276d6d7b3f1d73161527dade63233eb`。运行时正确拒绝了不匹配的内容，但开发启动只检查 npm 依赖锁，旧工具没有更新，启动器因而显示 `PORTABLE_TOOLS_INTEGRITY_FAILED`。

工具是 DSH 和命令执行环境所需的固定运行依赖。当前公开发行包配方可以独立重建并得到既有清单锁，不需要放宽校验或从系统 PATH 选择任意工具版本。

## 仓库中的唯一版本依据

- `resources/portable-tools/manifests/win32-x64.json`：新纳入 Git 的 10181 项完整逐文件清单，1832343 字节，使用固定 LF 行尾，SHA-256 为上述 `9ec34c…7996f`。
- `tool-lock.json`：固定完整清单的精确摘要与六种工具版本，保持拉取版本的原锁，没有为了适配本机旧文件而改写。
- `download-lock.json`：固定五份公开发行包的 URL、归档格式和 SHA-256。获取、组装、发布、修复与重建验收脚本随 Git 一并管理。
- 大型程序、下载缓存、旧包备份、实例与个人应用数据不提交到源码历史；完整清单和下载配方足以验证各机器取得相同工具。首次准备仍需联网，不能把普通 Git clone 解释为离线交付了全部二进制。

## 修复行为

`01` 会识别缺失或清单过期的工具。`npm run tools:repair` 可单独修复工具，无需重复安装 npm 依赖。两者都先组装新目录、运行工具探针并复现已提交的清单锁，再使用受项目路径约束的目录切换发布。旧包保留在 `.tools/portable-tool-backups`；替换失败会回滚。下载或校验失败不会移动旧包，修复不能与清单锁提升合用。普通获取仍拒绝覆盖已有目录。

`02` 与 `03` 在启动或构建前快速检查本地清单与仓库锁，发现工具过期会明确提示重新运行 `01`，不会再进入不可用的启动器。实际程序内的文件与入口程序校验继续保留。

打包后的实际 CLI 验收还发现，ConPTY 原先同时收到 `Path` 与 `PATH` 两个大小写别名，可能优先调用系统中另一份 `dsh`，使当前终端的固定上下文被旧命令拒绝。现将原环境复制成单一 `PATH`，把当前管理命令目录放在最前，清除旧的固定上下文别名后设置当前会话文件。只改变子进程环境，不更改系统或用户 PATH；原有目录边界、运行制品封印与上下文校验没有放宽。

附加构建检查也发现，本机媒体包获取记录还引用拉取前的旧 URL，新锁要求重新确认来源；无代理的下载在本网络超时。已用归档 SHA-256 与新锁一致的缓存重新执行媒体获取及完整校验，刷新来源记录。新锁中的 Windows 媒体下载地址通过代理实际返回 HTTP 200，文件长度与锁中 103539191 字节一致。没有放宽来源记录或媒体字节校验；`01` 负责同时准备媒体与便携工具，只修复便携工具不等于更新全部构建输入。

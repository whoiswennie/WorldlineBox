# 伙伴记忆规模实测与宿主热路径修正（2026-11-02）

本轮使用独立临时库、实际 BotStore / 原文投影器 / 常驻独立 VCP / 原始 CDS。720 条日记使用本机内置 EmbeddingGemma2 compact、768 维、CPU 和正式 HTTP bridge；未复制模型。全部聊天路由指向本地拒绝端点，未继承模型凭证，实际 Chat 请求数为 0。没有调用收费 LLM。

10,000 / 100,000 指用户、伙伴原始消息条数，并非向量日记条数；通过无回复收件人的入站事件写入 BotStore，不能据此声称主脑回复或 inbox 调度吞吐。日记与原文位于隔离域。硬件：i9-14900HX、32 逻辑 CPU、约 32GB RAM、Windows x64、Node 24.15.0 / ABI 137。

## 发现与实际修复

1. 原文每条消息重新读写完整 episode。改为一页内按 episode 分组，原始 JSON 原子 append 后才批量确认每个消息 ID；重启补确认不重复。1,000 条投影由 15.39 秒降至 0.71 秒；JS 读字节由 38.19MB 降至 1.52MB，写字节由 19.32MB 降至 0.98MB。
2. 每次回查都全量 reconcile，以及同步前后各一次原生 status。原 status 内部统计全部 messages，100k 时 25 次热回查造成约 5.18GB 进程读取。稳定常驻、无变更时复用已确认的同步代次；查询仍调用原始搜索接口，实际错误不会被缓存掩盖。显式 status 仍返回实时状态。
3. 修改的 episode 走原始 ingestHistoryPath；积压至少 16 个 episode 时走一次原始批量 reconcile，避免每个 path 单独提交 Tantivy。约 900 个积压 episode 的首次回查由 119.22 秒降至 6.97 秒。
4. 在宿主内维护目录映射，只有新增或改变目录元数据才重写 owner config / mirror manifest，写失败保留 dirty 状态重试。同一个 episode 追加时，实测目录 JSON 写入为 0；100k 时新增 episode 仍需写约 355KB 元数据。这保留原始格式和工具行为，未宣称目录结构在任意规模下均为 O(1)。

原始 405 个评分、检索、格式化与原生实现文件均未修改，staging 完整性检查继续通过。以上只修改宿主生命周期与存储适配。

720 日记总写入约 109.78 秒。10k 原文投影约 5.82 秒；之后新增约 90k 投影约 60.16 秒。已有 100,002 条原文的库完整关闭并使用新 Worker / CDS 冷启动，首次 TopicMemo 1.81 秒；这与未处理积压的 6.97 秒不同。重启后的 DeepMemo 阶段含一次 114ms 的首次原生搜索初始化，不把它隐藏为热缓存结果。

100k DeepMemo 25 次热查询的 JS 层读取约 14.7KB，无目录写入；TopicMemo 仍按原实现读取 owner 目录与目标 episode，约 5.14MB / 25 次。100k 同 episode 追加后回查约 149ms，新增 episode 后回查约 226ms，包含原始入账、目录更新、原生索引确认和读取，属于单次样本。

100k 热回查阶段所拥有进程的工作集采样约 474MB；加载真实 embedding 并保持两个记忆域后约 1.26GB。后者含内置 llama 服务、CDS、宿主、VCP 与 Windows conhost；6 个业务进程及各自 conhost 的具体 PID / 角色在原始 JSON 中。累计创建 3 个 VCP Worker，其中一个已因刻意重启而退出，并非同时驻留 3 个。工作集是阶段末采样，不能称为峰值或长期无泄漏证明。

## 证据及观测边界

- 最终完整原始结果：`artifacts/superagent-bot-development/memory-scale-2026-11-02T14-22-39-720Z/result.json`。
- 初始 1k 基线：`memory-scale-2026-11-02T13-59-37-485Z/result.json`；分批原文优化后：`memory-scale-2026-11-02T14-03-09-475Z/result.json`；100k 线性扫描基线：`memory-scale-2026-11-02T14-11-09-948Z/result.json`。这些路径均在上述 artifacts 目录内。
- 原始结果保留了一个仪表错误：restart 阶段旧、新 Worker 曾复用同一个探针文件，导致该阶段 JS 文件计数负数。**这个阶段的 JS 文件计数无效，不得引用**；时延、真实回查、OS 进程指标不受它影响。探针现已按 Worker 使用唯一文件，另用短 10k 轮验证；原始证据没有覆盖或删除。
- 仪表修复的短 10k 轮：`memory-scale-2026-11-02T14-28-55-881Z/result.json`，全部 JS 计数非负，冷重启原文成功、无 Chat 请求、临时根清理完成。这次只验证仪表，5 次样本不用于替代上表的 25 次结果。
- JS fs 探针只计 Node 公共 read/write/readdir，不覆盖 Rust、SQLite 或 llama 原生内部读取。Windows process I/O 包括管道、设备和网络，不等同于磁盘文件数。没有可靠的原生 DB 队列计时接口，因此 `dbQueue=null`，不推算或虚构。
- 目标代码命中是重复结构的合成单事实探针，不是自然聊天质量分数；计划、否定、时间范围、更正与真实模型调用质量由另一个正式验收 harness 检查。本轮不提供 100k 向量性能或数月持续运行结论。

新增 4 个宿主测试覆盖零变更热查询、批量原生对账、新 CDS 代次、目录 I/O 失败重试、拒绝 ingest 的真实重试，以及跨 100 条边界的 JSON 已落盘 / SQLite 未确认恢复。真实 VCP 原生测试同时验证先初始化搜索，再追加到原 episode 后可搜索原始新增内容。合计 8 项通过，相关 fixture / 测试定向 TypeScript 检查通过。
